# 每回战报固定格式

生成每回战报时读取本文件，并同时遵循 [chronicle-style.md](chronicle-style.md)。本文件定义内容结构，不等于最终文件版式；生成 Markdown、Word、PDF 或 TXT 时还要读取 [output-formats.md](output-formats.md)。默认生成完整编年史；只有用户明确要求时才缩写为简报。

严格保持八个编号栏目及最后的队伍状态摘要。固定的是信息架构，不是会议纪要式措辞。某栏没有内容时简洁写明 `本回无`、`未记录` 或 `无法确认`。

# 《Campaign 名称》冒险战报

## 第 X 回：有辨识度的回合标题

开头可以包括：

- 一句确实来自本回、能代表主题或笑点的引语；
- 实际队伍名单；
- 开始与结束等级或其他最重要的状态变化。

不要默认把时间戳范围、来源清单、术语异文和说话人方法放在最前面。只有确实影响阅读时，才在正文前加入最多数条简短的 `整理说明`；详细歧义写入 Ledger 的待确认项。

## ① 剧情经过

按事件顺序讲述本回故事，但按场景而不是转写段落组织。每次地点、目标、主要威胁、策略或情绪明显改变时，建立有内容的场景小标题：

```markdown
### 1. 场景标题

一两句建立处境。

你们采取了什么办法，谁做出了关键选择。

> “来自转写的重要原话。”

结果、代价或新的路标。
```

要求：

- 保留任务缘起、重要玩家选择、关键 NPC 对话、剧情转折和回末去向；
- 重要遭遇充分展开，小型重复行动可以合并；
- 默认使用“你们”保持跑团现场感，角色高光直接点名；
- 关键骰点只有在它解释成功、失败或笑点时才写，不要把全部检定塞进正文；
- 可适度使用短段落、粗体、引用和分隔线突出节奏，但不要装饰每句话；
- 不得为了文学性编造氛围细节、内心活动、反应或因果。

必要时使用 `【模组背景】`、`【玩家推测】` 或 `【尚未确认】`，但普通已确认事件直接叙述，不必重复贴标签。

## ② 各角色做了什么

按照 Campaign Profile 中的实际 PC 名单逐一建立小节，实际有几名就写几名：

```markdown
### 🧙 角色名｜职业

**本回关键词：关键词一、关键词二、关键词三。**

- 角色扮演、调查与重要对话；
- 关键决定及其影响；
- 战斗贡献与重要成功或失败；
- 关系、职责或个人状态变化。
```

Emoji 可按角色形象选用但不是必需。关键词必须有本回事实支持。不要把本栏缩成伤害统计，也不要逐句复制剧情正文。资料无法可靠归属某名角色时，明确写出识别限制，不得把匿名行动硬分给该角色。

## ③ 战斗记录

先用简洁表格总览正式战斗以及影响显著的战斗规避：

| 战斗 | 敌人 | 结果 | 关键事件 |
| --- | --- | --- | --- |
| 战斗 1 | 名称与可靠数量 | 胜利 / 失败 / 撤退 / 绕过 / 未决 | 决定性事件 |

表格之后按实际内容补充：

- 决定战局的战术、法术、检定或失败；
- 暴击、大失败、误伤、倒地、濒死、死亡与异常事故；
- **本回严重伤势 / 持续状态**，尤其是会延续到下一回的内容。

资料不足时不要编造逐轮记录。只在来源可靠时保留精确伤害、骰点和敌人数。

## ④ 获得的装备 / 金钱

先给出清晰的资金变化，再突出重要物品：

```markdown
### 金钱
- 每人 +100 gp；或队伍资金变化及最终余额。

### 重要装备
#### 🗡️ 物品名
- 持有者：角色名 / 队伍 / 未确定
- 来源：
- 已确认作用：

### 其他战利品与消耗品
- 物品 ×数量 → 持有者 / 未分配 / 归属未确定
```

战报以便于玩家阅读为主；完整来源、异文、数值冲突和历史转移写入 Ledger。不得假设平均分配，也不得把发现物品自动写成某角色拥有。

## ⑤ NPC 关系变化

只展开本回重要 NPC 及关系发生变化者。优先用“关系如何变化、为什么、如今怎样”的自然语言，而不是堆叠数据库字段：

```markdown
### NPC 名称

**关系：敌对 → 理解 → 被超度**

用数句说明本回发生的变化、角色为何作出决定，以及 NPC 当前状态。
```

再次出现的 NPC 必须与历史记录串联。只被提及、没有实际出现的幕后人物应明确说明来源，不要写成已经见面。

## ⑥ 已知线索

记录玩家角色当前知道的内容，而不是 DM 或模组的全部真相。可以按主线、NPC、地点、敌人、物品分类。

普通事实自然列出；NPC 尚未验证的证词写成“某 NPC 声称”；玩家自己的推理放入独立的 `玩家推测` 小节。不要给每一行机械添加 `[已确认]`。

## ⑦ 未解谜团

不要只给出一排问句。对核心谜团写出“目前知道什么”和“仍然不知道什么”：

```markdown
### ❓ 谜团标题

目前已知：……

仍待确认：……
```

次要谜团可以使用简短列表。后续解决后，从 Ledger 的未解谜团中移除，并在解决当回的剧情和线索中记录答案。不得用模组知识或模型推测自行解谜。

## ⑧ 本回名场面

选择最值得玩家回忆的真实片段：大成功、大失败、角色高光、桌上笑点、经典台词、玩家互动、意外事故或 DM 神来之笔。

完整战报通常把名场面写成简短小故事，而不是只有一句标签：

```markdown
### 🥇 名场面标题

当时发生了什么。

> “有来源支持的关键台词。”

为什么它改变了局势、体现了角色，或成为桌上笑点。
```

可以使用 `🥇 / 🥈 / 🥉 / 🏅 / 🏆`，数量随本回素材决定。幽默可以改善措辞，但不得改换行动者、夸大结果或伪造台词。

| 项目 | 状态 |

| 等级 | 按每名实际 PC 记录，或在完全一致时写“全员 X 级” |
| 当前地点 | … |
| 已完成事项 | … |
| 当前任务 | … |
| 下一目的地 | … |
| 金钱 | … / 无法确认 |
| 重要物品 | … |
| 重要 NPC | … |
| 主线状态 | … |

长模组同时更新独立的 `campaign-ledger.md`。战报只链接 Ledger 路径，不要把完整数据库内容追加进读者向正文；如果用户只要求在对话中输出、没有写文件，再在战报后以清楚分隔的独立区块提供新版 Ledger。

## 📖 本回结语

完整战报默认以简短结语收束。结语应回望本回真实发生的起点、关键选择或代价，并指向下一目的地、任务或悬念。

如果开场台词、人物承诺或意象与结尾选择自然呼应，可以点明这种呼应；没有自然主题时，就用事实性的悬念收尾。不得发明角色内心、强加道德结论或预告尚未发生的模组剧情。
